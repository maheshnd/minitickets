- **Step:** Feature 1, Step 5: cache stampede protection for `events.list` (would be `docs/25-*`).
- **Concepts:** cache stampede (many misses → many identical DB queries); single-flight (in-process, shares one promise; cleanup on success AND error); distributed lock in Redis (`SET NX PX` + random token, release via Lua compare-and-delete); double-check after taking the lock; bounded wait + fallback; lock limits (TTL expiry, Redis restart → extra query) and why that's fine for a cache but never for seats (two holders = double-sold seat; seats need DB guarantees). Also new: `LOG_LEVEL` env var.
- **Key files:** `apps/api/src/services/single-flight.ts` `singleFlight`; `services/events.ts` `listUpcomingEvents`, `rebuild`, `waitForCache`, `recheckCache`, `releaseLock`; `queries/events-cache.ts` `tryLockUpcomingRebuild`, `releaseUpcomingRebuildLock` (`RELEASE_IF_OWNER`); `queries/events.ts` `listUpcoming` (debug line); `config/env.ts` `LOG_LEVEL`; `scripts/stampede-demo.ts` (`pnpm demo:stampede`, RESP `DEL` over `node:net`).
- **Measured (local, 2026-10-12, DB queries = "db query" debug lines):** before fix: 1 instance × 100 req → **100** (2/2 runs). Level 1: 1 × 100 → **1** (3/3); 2 instances × 50 → **2** (3/3). Level 1+2 without double-check: 2 × 50 → 1 or **2** (2 of 5 runs gave 2). Level 1+2 with double-check: 1 × 100 → **1** (3/3); 2 × 50 → **1** (10/10), no warnings. All responses 200; waiting instance's max ≈ 65 ms (one 50 ms re-check).
- **Unsure / for the docs:** the Lua script is only unit-tested against a fake; it was checked by hand on the real Redis (wrong token → 0, key kept; right token → 1). Wait settings (5 × 50 ms, lock TTL 5 s) are judgement calls, not measured under real load. A waiter whose holder is slow still reads Postgres after ~250 ms.

- **Step:** Feature 1, Step 6: cache invalidation for `events.list` + admin role to create events (would be `docs/26-*`).
- **Concepts:** cache invalidation; write-then-invalidate order (INCR only after the insert commits; readers read the generation BEFORE Postgres); DEL vs generation key (`events:upcoming:gen`, cache key `events:upcoming:v1:g<gen>`, lock key `lock:…:g<gen>`); the stale-refill race (slow reader writes late → lands in the old generation, expires by TTL); bounded staleness (INCR fails → logged error, stale ≤ one TTL ~33 s, request still succeeds); RBAC (`users.role` + CHECK); 401 vs 403 (authn vs authz); per-layer staleness (Redis fixed at once, other browsers' React Query up to 30 s staleTime).
- **Key files:** `queries/events-cache.ts` `getUpcomingGeneration`, `bumpUpcomingGeneration`, `upcomingKey`, `upcomingLockKey`; `services/events.ts` `listUpcomingEvents` (gen first; single-flight key per gen), `createEvent`, `invalidateUpcomingList`; `queries/events.ts` `create`; `trpc/init.ts` `isAdmin`/`adminProcedure`; `trpc/context.ts` (role from Postgres every request); `services/users.ts` `makeAdmin` + `scripts/make-admin.ts` (`pnpm user:make-admin <email>`); `drizzle/0003_users_role.sql`; shared `CreateEventInput`, `UserRole`, `EmailSchema`; web `features/events/components/create-event-form.tsx`, `hooks/use-create-event.ts`, `app/admin/events/new/page.tsx`, `proxy.ts` (/admin), `header-nav.tsx`; `e2e/admin-events.spec.ts`; `scripts/stampede-demo.ts` now INCRs the gen key instead of DEL.
- **Measured (local, 2026-10-12, own API on :4101, LOG_LEVEL=debug):** create → "generation is now 2" (6.4 ms) → next `events.list` cache=miss, 1 db query, has the new event (4.3 ms) → next cache=hit (1.8 ms). Redis after: `g1` orphaned (TTL 26 s, expiring), `g2` live, gen key TTL -1. `pnpm demo:stampede -n 50` after a bump: 1 db query. Race unit test fails if the late write goes to the CURRENT generation (DEL-like), checked by mutation.
- **Unsure / for the docs:** role is read from Postgres in `createContext` on EVERY request with a session (one PK lookup), so role changes count at once; cost: logged-in cache hits now touch Postgres once. Alternative (role copied into the Redis session) was rejected: demotion would lag up to 7 days. Gen key has no TTL; under an `allkeys-*` eviction policy it could be evicted and restart at 0 (harmless unless an old g0 key is still alive). The INCR-fails path is unit-tested only (didn't stop the owner's Redis). make-admin is a dev tool (not in the image); on AWS the first admin would need a one-off task or psql (not built). Each e2e run adds one event + two users to the local DB (no delete API).
