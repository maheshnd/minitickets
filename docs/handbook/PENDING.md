- **Step:** Feature 1, Step 7: stale-while-revalidate (SWR) + stale-if-error for `events.list` (would be `docs/27-*`).
- **Concepts:** SWR (serve stale now, refresh in the background); soft vs hard TTL (fresh < soft ≤ stale < hard = Redis expiry, env `EVENTS_CACHE_SOFT_TTL_MS`/`_HARD_TTL_MS`, defaults 30 s / 5 min, Zod refine soft < hard); cache value `{ data, fetchedAt }` (Zod-checked) and key bump v1 → v2 (shape version); fire-and-forget background refresh (why safe: nobody needs the result, errors caught inside the single-flight work; limits: in-memory only, lost on exit, not a job queue); one refresh for many stale readers (reuses single-flight + Redis lock; a refresh never waits for another holder; double-check accepts only FRESH); stale-if-error (availability over freshness, hard TTL caps age); why invalidation overrides SWR (new generation = empty key = miss; never fall back to an older generation); request-log `cache` = fresh | stale | stale-if-error | miss | error. BUG FIX in this step: lazy authorization lookup — `createContext` no longer reads the role from Postgres (it made EVERY logged-in request depend on Postgres, so logged-in visitors got an error on `events.list` with Postgres down although stale-if-error had a copy); only `isAdmin` reads it, per admin request (role changes still count at once). Principle for the docs: a route must not depend on a lookup only other routes need (failure domains / blast radius). Links for the docs: React Query `staleTime` (same idea in the browser, already used for /events) and HTTP `Cache-Control: max-age=30, stale-while-revalidate=270, stale-if-error=…` (RFC 5861).

- **Step:** Feature 1, Step 8: filters for `events.list` (venue, from, to) + filter-aware cache keys (would be `docs/28-*`).
- **Concepts:** canonical keys (one form for "the same question": venue trimmed + lowercased, dates rounded to the start of the UTC day, fields sorted, empty ones left out; the SAME form feeds the SQL, the cache key, single-flight and the lock, else two different questions would share one answer); hashed keys (`events:upcoming:v3:g<gen>:<16 hex of SHA-256>`: short + safe from `:`/`*`/spaces; collision ≈ 1 in 37 M at 1 M keys; canonical text kept in a debug line `events cache key <key> = <canonical>`); key explosion and its bounds (canonical form, day rounding, range ≤ 1 year, hard TTL 5 min, one generation for all filters; venue is free text so NOT bounded: rate limiting would be the real fix, not built); eviction policies (`maxmemory 256mb` + `allkeys-lru` in docker-compose; noeviction = writes refused; trade-off: sessions share this Redis and can be evicted too; the gen key is read on every request so LRU practically never picks it); jitter BACK on the SOFT TTL (0-10%, stored per value as `staleAt`, clamped ≤ hard TTL; why now: many keys refilled together after a bump would all refresh together; why not in Step 7: one key = one refresh); one INCR invalidates every filter key (vs SCAN + DEL one by one: slow, not atomic, stale-refill race per key); URL as state (shareable, reload/back keep it, server renders it; GET form works without JS); React Query key includes the input, so the page passes ONE input object to both prefetch and `useEvents`; explain-only: user/locale/currency MUST be in the key once responses depend on them (no prices or per-user list yet).
