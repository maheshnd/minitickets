# Step 10: CI with GitHub Actions

CI (Continuous Integration) means: every time code is pushed, a computer we do not own checks it
automatically. If a check fails, we find out in minutes, not after a bad merge. There is no
deployment yet; this step only checks.


## New local checks

- **Lint** (`pnpm lint`): ESLint with `typescript-eslint` for all packages, plus the Next.js and
  React rules for `apps/web`. It catches mistakes the compiler allows, such as unused variables or
  reading a React ref while rendering. Settings: `eslint.config.mjs`.
- **Unit tests** (`pnpm test`): Vitest, which uses the same `describe` / `it` / `expect` style as
  Jest. Test files are named `*.test.ts` and sit next to the code. They are fast and need no
  server or database:
  - `getSafeNext` accepts `/dashboard` and rejects `//evil.com`, `/\evil.com`, `https://evil.com`.
  - `errorMapper` turns `NotFoundError` into `NOT_FOUND`, `ConflictError` into `CONFLICT`, and
    leaves a plain `Error` as `INTERNAL_SERVER_ERROR`.
  - `SignupInput` lowercases the email and rejects different passwords.
- **Pinned tools:** `.nvmrc` holds the Node version (24.13.0) and `packageManager` in the root
  `package.json` holds the pnpm version. CI reads both, so CI and your laptop use the same tools.

## What CI runs (`.github/workflows/ci.yml`)

It runs on every push and every pull request, in two jobs.

**Job `quality`** (10 minute limit): install, then `pnpm typecheck`, `pnpm lint`, `pnpm test`.

| Check     | Why it exists                                                      |
| --------- | ------------------------------------------------------------------ |
| typecheck | TypeScript finds type errors across all three packages.            |
| lint      | Finds likely bugs and style problems.                              |
| test      | Small, fast tests of the logic that matters most (security, errors). |

**Job `e2e`** (15 minute limit, starts only if `quality` passed): runs the Playwright browser
tests against the real app. It starts Postgres and Redis, runs the migrations, installs Chromium,
and runs `pnpm test:e2e`. If it fails, the Playwright report is uploaded as an artifact you can
download from the run page. It waits for `quality` so we do not spend minutes on a browser run when
a quick check already failed.

In CI, `playwright.config.ts` starts the API and the web app itself (the web app as a production
build: `next build` then `next start`). On your laptop it does not start anything; it uses the
servers you already run with `pnpm dev`.

## Why these choices

- **`--frozen-lockfile`**: `pnpm install` normally may update `pnpm-lock.yaml`. In CI that would
  hide a mistake, like a `package.json` change committed without its lockfile. With this flag the
  install fails instead, so CI always installs exactly the versions we committed.
- **Service containers**: the e2e tests need a real Postgres and a real Redis. GitHub starts them
  as Docker containers next to the job, with the same pinned versions as `docker-compose.yml`
  and healthchecks, so the steps only begin once both answer. Every run gets a fresh, empty
  database, so tests never depend on leftovers. The passwords in the workflow belong to this
  throwaway database only; they are not real secrets.
- **Least-privilege `permissions: contents: read`**: every job gets a token to talk to GitHub.
  By default that token can be powerful. We list only what we need (read the code). If a
  dependency or a workflow step were ever compromised, it could not push code or change the repo.
- **Concurrency cancel**: if you push twice quickly, the first run is already out of date. The
  `concurrency` setting cancels it, which saves time and money and shows only the newest result.
  Runs are grouped per branch, so branches do not cancel each other.
- **Cached Chromium**: downloading a browser each run is slow. We cache it, keyed by the
  lockfile, so it is downloaded again only when Playwright changes.

## How CI will gate CD later

CD (Continuous Deployment) will be a later step. The plan: deploy only when CI is green. In GitHub
we will turn on branch protection so `main` needs both jobs (`quality` and `e2e`) to pass before
a merge, and the deploy workflow will start only after CI succeeded on `main`. That way broken
code can be merged by nobody, and so can never be deployed.
